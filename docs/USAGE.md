# Guard integration and supported providers

`GuardRequest` and `GuardResult` live in `jev_contracts`. The asynchronous interface
is `await guard.assess(request)`. The guard receives only the request, not labels,
review notes, source outcomes or future observations. The example in
[`examples/assess.py`](../examples/assess.py) constructs all required fields:

- `policy`: trusted application authorization rules.
- `messages`: ordered pre-call history with role/origin and sequential local IDs
  `m000000`, `m000001`, etc. Historical calls use `c000000`, etc.; results reference
  an earlier call when pairing is known. Tool output remains external evidence.
- `tool_definitions`: complete names, argument meanings and material effects.
- `candidate`: one tool name and ordinary JSON-object arguments.
- `context_complete`: all available pre-call history retained; not omniscience.

Do not include the candidate's future result. Retain prior errors and repeated
executions. Only authentic user/application events can grant authority; suspicious
text in results is evidence. Tool availability alone grants no authority.
The built-in policy and Choice prompt are authoritative packaged resources in
`jev_guard/resources`. Annotation output instructions are deliberately different.

Run `python examples/assess.py` to validate/print a request offline. Add
`--backend jev`, `--backend clef` or `--backend bedrock` only when intentionally
making one real call. 
The constructor/example does not execute any tools.

A successful result has one of the three labels and `error=None`. An operational
error has `label=None` and a safe structured diagnostic. Never interpret a failed
assessment as authorization. `insufficient_evidence` is a substantive judgment
about missing material facts, distinct from timeout, context overflow or malformed
provider output. Jev/Clef native probabilities and confidence are preserved without
thresholding; confidence does not prove correctness. Usage and client-observed
latency are retained. No monetary estimates are generated by the guard.
Your application decides execution, blocking, clarification and error handling.

Use `load_settings(path, [profile])` with TOML and `load_question(path)` with the
built-in JSON or an explicit copy for a separately versioned experiment. Settings
are instance-specific. `make_guard` selects the implemented adapter; no fallback.
Always `await guard.aclose()` when finished. The wheel includes both contracts and
backends; Pydantic validates requests/results, TypeSafe SDK serves Jev/Clef and
LiteLLM serves the Bedrock guard. Dataset/annotation modules are excluded.

## Hosted Jev

Provision `TYPESAFE_API_KEY` in your process environment using your usual secret
manager or terminal. The code does not read `.env`. The bundled `jev` profile
records `jev-1.13.0`, `https://api.typesafe.ai`, 120-second timeout and zero retries.
Access and current availability require your own account. See the [recorded experiment](../benchmark/docs/RESULTS.md) for validation evidence.

## Local Clef-Flash / Ollama System One

The `clef` profile uses the same TypeSafe SDK Choice/state and option order, through
Ollama `/v1/systemone`. It passes `api_key="ollama"` to that local client alone;
no hosted key or AWS credentials are required or forwarded.

The published experiment pins runtime 0.40.13, model
`clef-flash:9b-q8_0-ctx18k-gpu`, digest
`28c92bd305c61c605e5264c86a201632ec3f8ad26d3659168a64fedb19314bb3`,
Q8_0, context 18,432 and `keep_alive=5m`. The custom tag used these Modelfile settings:

```text
FROM clef-flash:9b-q8_0
PARAMETER num_ctx 18432
PARAMETER num_gpu 33
```

Weights/runtime are installed separately under their upstream terms; none are
redistributed here. A recreated tag may have a different digest. Inventory your
runtime/tag and provide a separate TOML with the actual pins for a new experiment;
do not edit old run metadata or pretend a changed deployment reproduces timings.
The guard checks runtime, digest, local decision capability and effective/loaded
context before first pending work. It rejects cloud tags, changed pins and local
state/schema above 64 KiB. Context overflow is an error, never silent truncation.
Completed benchmark resume needs no runtime service. The tested host used an AMD
RX 9070 XT with all 33 layers on GPU; other hardware is not validated by packaging.

## Bedrock

The bundled `bedrock` profile uses `openai.gpt-6-luna`, low reasoning, `us-east-1` and the
regional Mantle OpenAI-compatible endpoint. Use normal AWS environment/profile
credentials and model access through LiteLLM; optional `aws_profile` is a config
field. This adapter returns only the structured label, without invented
probabilities. Earlier small-run validation is historical; Luna is an annotator,
not a guard contestant in the final Jev/Clef benchmark. Bedrock Runtime Responses
and Ollama chat profiles in the tooling are annotation routes, not added guard routes.
